# DotOffice

Pure managed .NET library for converting office documents — no LibreOffice, no native binaries, MIT licensed.

> **Status:** early development. Not usable yet.

```csharp
await DocumentConverter.ConvertAsync("invoice.docx", "invoice.pdf");
```

## Goals

- DOCX/XLSX/PPTX → PDF with high fidelity
- 100% managed code: runs anywhere .NET runs (containers, Linux, AOT)
- No GPL/AGPL or restrictive-license dependencies

## Packages

| Package | Purpose |
|---|---|
| `DotOffice.Core` | Format-neutral document model |
| `DotOffice.Fonts` | OpenType parsing, subsetting, font resolution |
| `DotOffice.Pdf` | Low-level PDF writer |
| `DotOffice.Layout` | Line breaking, pagination, tables |
| `DotOffice.Docx` / `Xlsx` / `Pptx` | OOXML readers |
| `DotOffice.Converter` | Public facade |

## Roadmap

1. PDF writer + font embedding/subsetting ✓
   - **CFF-outline fonts** (OpenType `OTTO`, e.g. Noto Sans CJK, also inside `.ttc` collections; `CffFont.cs`): loaded for metrics, cmap and shaping like TrueType fonts, and embedded as `CIDFontType0C`. The subset keeps the original glyph ids and the CID-keyed charset (PDF character ids are the charset's CIDs), empties the charstrings of unused glyphs and inlines the subroutines of the kept ones, which are then dropped (they would be most of a CJK font's size: a three-line CJK PDF is 150 KB instead of 6 MB). Charstrings are never interpreted beyond the subroutine and hint-mask bookkeeping, so there is no outline access: glyph extents (used for mark attachment) are reported as empty. Not done: CFF2 and variable fonts, name-keyed CFF fonts in `.ttc` were not tried, and a glyph used for two different texts keeps one ToUnicode entry. Verified: a rendered PDF of Japanese text (`pdftotext`, `pdftoppm`) shows the right glyphs upright at a 14 pt pitch, and unit tests on the installed Noto Sans CJK (they pass without checking when it is absent); not checked in other PDF viewers
2. DOCX → PDF: paragraphs, styles, lists, tables, headers/footers, images ✓
3. DOCX polish: fields, floats, columns, footnotes, complex scripts including Indic, Sinhala, Tibetan (Universal Shaping Engine), Khmer and Myanmar ✓ (Sinhala, Tibetan, Khmer and Myanmar output was checked against LibreOffice and libharfbuzz, not Word; generated documents only show what DotOffice and LibreOffice do)
   - **Text boxes and shapes** (`StoryShapes.cs`, `TextBoxes.cs`): a `wps:wsp` in a `wp:anchor` (inside `mc:AlternateContent` the `mc:Choice` is read, so the VML fallback is never used) becomes a floating box with its `w:txbxContent` laid out inside the insets (`lIns`…, defaults 0.1″/0.05″), vertical `anchor`, solid fill, outline (width, dash, colour with `lumMod`/`lumOff`/`tint`/`shade`; theme colours from the document's theme, else the Office palette), rotation, and the same position/wrap/behind-text rules as floating pictures; content that does not fit is clipped. Colours may also come from `wps:style` `fillRef`/`lnRef` (index ≠ 0, colour only: the theme's line widths and fill styles are not read, so the line width is 0.75 pt when `a:ln` gives none). Outlines: the basic presets (rectangle, rounded rectangle with its `adj`, ellipse, triangle, right triangle, diamond, parallelogram, trapezoid, hexagon, pentagon, octagon, plus, chevron, pentagon arrow, five-pointed star, the four block arrows and the flow-chart process/alternate process/terminator/connector/decision/data/preparation shapes) are filled and outlined with the shape code of the spreadsheet drawings; linear and path gradient fills are real gradients clipped to the outline. Text goes in the insets of the frame, or of the inscribed rectangle for an ellipse (14.6 % each side) and of the corner arc for a rounded rectangle (29.3 % of the radius); other presets use the frame, which Word does not (their text rectangle differs). Inline shapes (`wp:inline`) take their size in the line, stand on the baseline and are drawn where they fall. Still skipped, with a warning: other presets (text kept, no fill or outline), picture/pattern fills (the first color), vertical text, groups (`wpg`), VML `pict`/`object`, transparency (`alpha`), shadows. Text-box auto-fit is not applied (the stored size is used). Verified: unit tests for the reader and layout relations and rendered synthetic files; **not** compared against Word (none available)
   - **Page borders** (`w:pgBorders`, `LayoutEngine.AddPageBorders`): per-edge style, width, colour and `space`, `offsetFrom` page (space from the page edge to the line) or text (space outside the margins), `display` (all / first page of the section / not first), `zOrder` front or back. Top and bottom lines run over the outer width of the side lines so corners meet. Art borders (`apples` …) are drawn as one single line with the warning `docx.page-border-art`. Not done: the header and footer are not included in a text-relative frame (Word extends it with `bordersDoNotSurroundHeader/Footer` off), and double/triple lines are centred on the edge, so against LibreOffice a text-relative double frame is about 2 pt off while a page-relative one matches. Verified: unit tests of the geometry relations and a rendered file compared with LibreOffice; **not** compared against Word
   - **Floating tables** (`w:tblpPr`, `FloatingTables.cs`): `horzAnchor`/`vertAnchor` (text, margin, page), `tblpX`/`tblpY`, `tblpXSpec`/`tblpYSpec` (left/center/right/inside/outside/top/bottom; inside and outside are left and right, swapped on even pages with `mirrorMargins`, as for frames and for pictures anchored to the inside/outside margin; checked by unit tests; LibreOffice 25 does **not** do it for a frame with `xAlign="outside"` and `mirrorMargins` — it puts the frame at the left on both pages, where we put it right on odd pages and left on even ones, as the spec says; not checked against Word), and `leftFromText`… distances. The table is laid out once, then placed and wrapped like a floating picture (square wrap, text goes to the wider side), so following paragraphs flow beside it; its own `jc` and `tblInd` do not apply. `tblpYSpec="inline"` is an ordinary table. A table anchored to the text moves to a new page when it does not fit below the cursor. A table taller than a page cannot float: it is laid out in the flow with the warning `docx.floating-table`. Not done: floating tables inside cells, headers or footers (laid out in the flow), a table that splits across pages, a floating table following its anchor paragraph when that paragraph moves to the next page, merging of consecutive floating tables with equal `tblpPr`, and the `tblOverlap` rule. Verified: unit tests of reader and layout relations; a synthetic file placed the same vertically as LibreOffice, horizontally about 9 pt to the right of it (LibreOffice puts the table edge differently); **not** compared against Word
   - **Line numbers** (`w:lnNumType`, `LayoutEngine.NumberLines`): every body paragraph line (wrapped lines and empty paragraphs included; not table rows, text boxes, notes, headers) is counted; `countBy` shows every nth number, `start` the first, `restart` newPage / newSection / continuous, `distance` the gap left of the column, and `w:suppressLineNumbers` skips a paragraph. The number is right-aligned in the paragraph mark's font. Word's automatic distance (no `distance` attribute) is a guess of 14.5 pt (what LibreOffice uses); the font is the paragraph mark's, not the "Line Number" style. Verified: unit tests of the counting and position relations, a rendered file compared with LibreOffice (same numbers and baselines); **not** compared against Word
   - **Gutter and mirrored margins** (`w:pgMar/@w:gutter`, `w:mirrorMargins`, `LayoutEngine.Page.Margins`): the gutter is added to the left margin; with `mirrorMargins` the left and right margins are the inside and outside ones and swap on even-numbered pages (the page number, as for even headers), which moves the text, headers, footers, floats anchored to margins and page borders. Not done: `gutterAtTop`, `rtlGutter`, and `bookFoldPrinting`. Verified: unit tests of the positions; **not** compared against LibreOffice or Word
   - **Automatic hyphenation** (`w:autoHyphenation` in settings, `w:suppressAutoHyphens` per paragraph, `Hyphenation/Hyphenator.cs`): a word that does not fit the rest of the line is split at its last Liang pattern point that fits, the first part ending in `-`, with LibreOffice's `hyph_en_US` patterns (2 letters before and 3 after the hyphen; embedded, one resource per language so others can be added). Off unless the setting is on. Only words made of letters are hyphenated (accented letters included, though the English patterns know nothing about them, so they only add no points of their own); a word with a digit or symbol inside stays whole. A word split over runs (a bold or italic part in the middle) is hyphenated too, with the hyphen ending the run that holds the point. The language comes from `w:lang` (`w:val`; run, style or document default) of the word's first run, and picks the `hyph_<lang>.dic` resource: exact tag, then the primary language (`de-AT` → `de` → any `de_*`, so `en-GB` uses the US English patterns, which differ from British ones). A language with no embedded patterns is not hyphenated; with no `w:lang` at all the word is taken as US English. Only `en_US` ships (no other dictionaries are installed here and none were invented), so every other language stays unhyphenated until its file is added. `w:hyphenationZone` (default 360 twips, as in Word) leaves a word whole when the text before it already ends within the zone of the right margin; `w:consecutiveHyphenLimit` caps the lines in a row that end in a hyphen; `w:doNotHyphenateCaps` skips words with no lowercase letter. Words are hyphenated mid-paragraph as well, not only at its end. A bookmark (or other zero-width marker) inside a word does not stop it being hyphenated; the marker moves to the next line when the hyphen falls on it. Text directly followed by a field or picture is hyphenated on its own part (the hyphen never falls at the join, and the pattern run sees only that part). Not done: patterns for other languages, a per-run language inside one word, a field or picture at the start or in the middle of a word (the text after it is not looked at). Verified: unit tests of the patterns and the breaks; LibreOffice here has no hyphenation dictionaries installed and did not hyphenate the test file, so there was nothing to compare, including the three options above; **not** compared against Word
   - **Latin–East Asian auto-space** (`w:autoSpaceDE` for letters, `w:autoSpaceDN` for digits, both on by default, per paragraph and style): at each boundary between East Asian text and Latin text or digits the atom before the boundary is widened by a quarter em of its own size, the spec's width. Verified: unit tests (`AutoSpaceTests.cs`) of both directions and of switching each off. LibreOffice, checked on a Noto Sans / Noto Sans CJK JP line at 14 pt, adds a fifth of an em (2.8 pt) in both directions; we keep the quarter em (3.5 pt). Differs too: LibreOffice's lines with CJK text are 1.84 em tall whatever the Latin font, taller than the font's own 1.448 em (the OS/2 win metrics we follow; Word was not checked), so mixed lines are about 4 pt shorter here. A word split to fit a line keeps the space after its tail; **not** compared against Word.
   - **Vertical punctuation forms** (`UprightText.cs`, `TextShaper.VerticalGlyph`): an upright East Asian character in text running down (`tbRl`) is drawn with the glyph the font's `vert` feature gives it (、。「」ー, small kana and the like) at the unchanged pitch. A font without `vert` for a character leaves it as is. Verified: unit tests (`VerticalFormsTests.cs`, Noto Sans CJK JP, skipped without it) and a picture of a tbRl line compared with LibreOffice, whose glyphs for 、。「」ー are the same. Not done: `vrt2`/`vrt` fallbacks, `vkrn` kerning and `vert` for upright characters in btLr or counter-clockwise text, which stay fully turned; **not** compared against Word.
   - **Vertical text in table cells** (`w:textDirection` `btLr` and `tbRl` in `w:tcPr`, `TableLayouter.LayoutVertical`): the cell's content goes through the horizontal flow in a frame as long as the row is high (fixed row height, else the unwrapped text, capped at the section's body height so longer text wraps and the row grows across the lines) and as wide as the cell's inner width, and the frame is turned a quarter about the content box's centre (`btLr`: lines run up, the first at the left; `tbRl`: lines run down, the first at the right). The cell's vertical alignment places the lines across its width. In `tbRl` cells East Asian characters stay upright (see vertical text in sections). `tbRlV` is read as `tbRl`. `lrTbV` and `tbLrV` are read as horizontal text, as LibreOffice 26.8 lays them out (checked with `soffice`); for `lrTbV` that is the intended result, while a literal `tbLrV` (text running down, lines stacked left to right) would need a mirrored frame, not a rotation, and is not done. Not done: splitting a vertical cell over pages: its lines are one unsplittable slice, so a row holding a vertical cell that does not fit the rest of a page moves whole to the next page (as with `cantSplit`; covered by a layout test only, a `soffice` comparison was inconclusive because the default fonts differ). In an auto-width table a vertical cell asks for the width of its stacked lines (laid out at the unwrapped length, capped at the body height), not for its text length; in a row of fixed height the lines are wrapped at that height (single-row cells only; rows merged vertically use the unwrapped length), and the column is not compared against `soffice`. LibreOffice 26.8 does not grow an auto-height row for vertical text (it stays one line high and clips), so the cap follows the spec/Word intent, not LibreOffice. Verified: layout tests, and the first-line position and start corner against LibreOffice (`pdftotext -bbox`) for both directions; **not** compared against Word
   - **Vertical text in sections** (`w:textDirection` `tbRl`/`tbRlV` and `btLr` in `w:sectPr`, `LayoutEngine.Turned`): the section is paginated on the page turned a quarter (width and height swapped, margins turned with it, so lines are horizontal and as long as the page is high between its margins) and `Render` turns the finished page back with one `PushItem` about the page centre. `tbRl`: lines run down, the first at the right margin, stacking leftwards; `btLr`: lines run up from the bottom, the first at the left margin, stacking rightwards. A change of direction between sections starts a new page. East Asian characters (ideographs, kana, Hangul, full-width forms; `UprightText`) stay upright in `tbRl` text, each drawn in a group turned back about the centre of its em square, while Latin letters turn with the line, as LibreOffice 26.8 does (checked with `soffice`: 14 pt pitch down the line, Latin run sideways in the same column); `btLr` text stays fully turned. Vertical glyph forms for punctuation and the Latin–East Asian auto-space are covered by their own entries below. Compared with LibreOffice with Noto Sans CJK JP at 14 pt: the pitch down the line (14 pt) and the sideways Latin run agree; the column sits about 4.7 pt nearer the margin than in LibreOffice, whose lines of mixed fonts are taller (25.8 pt against 21.8 pt between lines), so that is a line-height difference, not the glyph centring. LibreOffice 26.8 lays `btLr` out exactly like `tbRl` in a section (checked with `soffice`); the spec's `btLr` is kept here. Headers, footers, footnotes, floats, columns, line numbers and page borders are turned with the page. Checked against LibreOffice 26.8 for `tbRl` (same font size): the body start corner, two columns (line breaks and stacking) and line numbers (above the first line, one per line) agree; headers and footers differ: LibreOffice keeps them horizontal at the physical top and bottom of the page, while here they are turned with the text (header on the right edge, footer on the left), which is the Word/spec intent, so that stays. Page borders keep their physical edges (each logical edge takes the border of the physical edge it lies on) and, with `offsetFrom="text"`, sit 10 pt out from the text box as in LibreOffice (checked within 1 pt); LibreOffice also applies `offsetFrom="text"` when the attribute is missing, where the spec default (page) is kept here. Footnotes agree too: the note area sits on the left edge (the logical bottom), its lines run down from the top margin, and the body lines break at the same positions (within about 1.5 pt across the line). Floating pictures and text boxes stay upright (they are drawn against the turn of the page) and their wrap rectangle is the turned one (width across the lines): positions are read in the turned frame, so the offsets run along and across the lines, and the box hangs from the corner the turned rectangle has, as LibreOffice places it (checked for `tbRl`: box at the same corner, 100 x 60 pt upright, text wrapped around it; LibreOffice fills both sides of the box, while text goes on the wider side here, as in horizontal sections). Floating tables and frames are still turned with the page, and floats in headers and footers use the same rule without a comparison. Not compared against Word, and the offset frame (turned, as LibreOffice does) is not confirmed against Word. Verified: layout tests, and the `tbRl` start corner, line direction and stacking against LibreOffice; **not** compared against Word
   - **Vertical text in text boxes** (`bodyPr vert`, `TextBoxes.Realize`): `vert270` turns the text a quarter counter-clockwise (lines run up, first line at the left) and `vert`/`eaVert` clockwise (lines run down, first line at the right). The text is laid out horizontally in a frame as long as the body is high and turned about the body's centre; `anchor` places the lines across the box width, with the first line on the `t` side. East Asian characters stay upright in clockwise text (`vert`/`eaVert`), as in vertical cells and sections; counter-clockwise text turns them with the line. Insets stay physical (left/top/right/bottom of the unturned box). Not done: stacked (`wordArtVert`) and Mongolian text (laid out horizontally, with a warning). Verified: layout tests, and first-line position and start corner against LibreOffice for `t`/`ctr`/`b` anchors; **not** compared against Word
   - **Run border and emphasis marks** (`w:bdr`, `w:em`; `Flow.DrawRunBorders`, `Flow.DrawEmphasis`): a run border is a box (any line style, `space` padding, auto color = text color) around each stretch of adjacent atoms with the same border; it widens the text by its `space` plus the line width on each side (`TextLayout.BorderSpace`; the first atom of the stretch gets a leading pad, the last a trailing one), as LibreOffice does (checked with `soffice`: 5 pt each side for `space=4`, `sz=8`), but not the line height. `em` dot, comma and circle draw a mark at the top of the line box over each non-space character, `underDot` at the bottom. Marks are my own shapes (dot, ring, dot with tail), not font glyphs, and sit where LibreOffice puts them (top and bottom of the line box) without changing line height. `w:fitText` is read nowhere and ignored on purpose: LibreOffice ignores it too (checked with `soffice`), though Word stretches the run to the given width. Verified: unit tests, `soffice` rendering of the same markup for placement; **not** compared against Word
   - **Paragraph frames** (`w:framePr`, `FloatingTable.BuildFrame`): a paragraph with a frame floats; consecutive paragraphs with equal `framePr` share one box. `w`, `h`/`hRule` (exact or at least), `hSpace`/`vSpace`, `hAnchor`/`vAnchor` (text, margin, page), `x`/`y`, `xAlign`/`yAlign` (inside and outside read as left and right, as for floating tables), and `wrap` (around, auto, tight and through wrap square; none and notBeside leave no text beside) go through the floating-table placement and wrap code. Without `w` the frame is as wide as its widest paragraph's text, up to the column. Drop caps (`dropCap` drop or margin, `lines`) are frames whose box is exactly `lines` lines of the following paragraph high (the letter may be taller and overflow), so the text beside it runs for exactly that many lines; with an explicit `h` that height wins. The letter is not shrunk to fit as LibreOffice does; the number of lines beside it matches `soffice`. Frames in headers and footers float at their position (page, margin or column; a paragraph anchor means the top of the story) and, like other floats there, push nothing aside; LibreOffice 25 ignores `framePr` in headers and lays the paragraph out in the flow, where we follow the spec. Frames in table cells and text boxes are laid out in the flow as ordinary paragraphs, which is how Word is generally understood to treat `framePr` there (unit test, and a table cell with a right-aligned frame checked against `soffice`: it too lays the framed paragraph out in the cell's flow, and every x position agrees within 0.2 pt; the lines are 2–3 pt further apart here, the known line-height difference; Word was not checked). Not done: frames taller than a page (warning `docx.frame`), `anchorLock`, and frame borders and shading as one box (each paragraph keeps its own). Verified: unit tests; the position and wrapping of a right-aligned frame in the body match `soffice` (frame x of 420.1 pt, first line beside it), header frames are by unit test only; **not** compared against Word
   - **Right-to-left tables** (`w:bidiVisual`, `TableLayouter.cs`): the columns run from the right edge, `tblInd` counts from the right edge (ISO 29500 17.4.51), and the alignment is read relative to the leading (right) edge, so an absent or `left`/`start` `w:jc` puts the table flush right. That last point and the cell margins and borders (`left`/`right` stay physical, not start/end-mirrored) are my reading of the spec, not checked against Word. Cell paragraphs are not made right-to-left by the table (they carry their own `w:bidi`)
   - Known divergences from Word: the shared text layer takes LibreOffice as its model in places where Word behaves differently. The target is Word's output; LibreOffice is only a reference to check against
     - **Line height** (`FontSelector.cs`, `FontMetrics.Of`) follows Word's GDI model: the OS/2 win ascent and descent, plus the external leading (`max(0, hhea lineGap − (win sum − hhea sum))`) below the baseline, each rounded to twips; fonts without win metrics use hhea; USE_TYPO_METRICS is ignored, as in Word. This replaces the earlier LibreOffice `ImplCalcLineSpacing` model for DOCX **and** XLSX (the shared text layer; XLSX line heights change for fonts whose hhea and win metrics differ, e.g. Noto Sans). Office fonts such as Calibri, Arial and Times New Roman come out as before. Verified: unit tests of the formula (including a Noto copy with the typo flag cleared); reasoning from the published font tables (Arial 1.149, Times New Roman 1.149, Calibri 1.220 em, matching Word's known single spacing); **not** compared with PDFs exported from real Word. Where to place the leading (below the baseline here) is a guess. LibreOffice on Linux takes Noto Sans from hhea/typo (1.362 em) where this model gives 1.519 em, so single-spaced lines are 2–3 pt shorter in `soffice` at 14 pt; this was investigated and left as is: Word on Windows reads the win metrics through GDI, and LibreOffice's choice depends on platform and font flags, so the difference shows up against LibreOffice only
     - **Ligatures** (`TextLayout.cs`, `RunProperties.Ligatures`): DOCX runs have no optional ligatures (liga, clig) unless they carry `w14:ligatures` with a value other than `none`, which is what Word does (MS-DOCX 2.6.2.x; not checked against a Word export, no Word available). Any non-`none` value turns on both liga and clig; the historical and discretionary sets are not told apart. XLSX and PPTX text keeps ligatures on (unchanged). Text with character spacing still has none, as in LibreOffice and unverified against Word
     - **Bidi in `w:rtl` runs** (`TextLayout.BidiLevels`, `TextLayout.Reorder`): a stretch of adjacent `w:rtl` runs is ordered as a right-to-left isolate (RLI ... PDI) inside the paragraph, whose own direction and alignment stay as set by `w:bidi`; the isolate's ends act as paragraph-level separators when a line is put in visual order (`Atom.Isolate`), so a plain run next to the stretch is never reversed together with it. Whitespace in such runs is not reset to the paragraph level at the line end. Compared with Word 2016 (one version, small samples; Arial 16 pt): (1) six lines of Hebrew with Latin, digits, brackets and punctuation, every run `w:rtl`, in a `w:bidi` and a plain paragraph: visual order, spaces and bracket mirroring match; (2) a second document with eight paragraphs, each in a `w:bidi` and a plain version, plus three wrapped ones (Latin-only `w:rtl` text, a tab, mixed-run cases, wrapped Hebrew, Latin and mixed text), the mixed-run cases being: `w:rtl` "H abc " + plain "x y" (Word: "x y abc H" in a `w:bidi` paragraph, "abc H x y" in a plain one); plain "abc ", `w:rtl` "H xyz", plain " def" (Word: "def xyz H abc" and "abc xyz H def"); `w:rtl` "abc ", plain H, `w:rtl` " def" (Word: "def H abc" and "abc H def"). Order and x positions of the words agree for all of these (the rule, the isolate, is inferred from these few paragraphs only). Known differences from Word: plain (non-`w:rtl`) Hebrew in a `w:bidi` paragraph, which Word sometimes draws with reversed letters, is ordered normally here; trailing spaces at the end of a line in a plain paragraph, which Word keeps visible at the left (3 trailing spaces after a `w:rtl` run: Word's text starts 13 pt in, ours at the margin) and the layout trims; mixes of more than three runs, or with digits and punctuation across run boundaries, were not tried against Word.
     - These are shared with XLSX, so fixing them may shift XLSX output a little too
4. XLSX → PDF: milestone 1 ✓ (cells, styles, number formats, merges, page setup, print areas/titles, breaks, headers/footers); milestone 2 ✓ (rich-text runs, rotated and stacked text, gradient fills, pictures from drawings with anchors/crop/rotation, conditional formatting, fraction formats)
   - Milestone 3 ✓ (flipped pictures, multiple print areas, standard paper sizes, the workbook's `[ColorN]` palette, comments as an end-of-sheet list, shapes and charts, and the conditional-formatting leftovers below)
   - Milestone 4 ✓ (chart types and options, shape fills, arrowheads and paths, conditional formatting across sheets, custom icons and data-bar axes, pivot tables without a blanket warning, all paper sizes, first page numbers, fill alignment)
   - Milestone 5 ✓ (BMP, GIF and TIFF pictures; print titles outside the print range and headers/footers that scale with the sheet; chart transparency, trendlines, error bars, manual layouts and a category axis that follows a reversed value axis; pattern fills, theme gradient styles, shadows and custom geometry with guide formulas; lookup and reference functions, whole-column references and x14-only data bars in conditional formatting; pivot styles of the common Light and Medium families and pivot-area formats)
   - Milestone 6 ✓ (RLE-compressed BMP and LZW TIFF pictures; header and footer pictures; trendlines on bars and stacked groups with equation and R² labels, chart text styles and a manually placed legend; blurred shadows, picture fills and rectangular path gradients on shapes; conditional-formatting sums, counts, date, text and math functions, R1C1 `INDIRECT` and empty text as non-blank; every built-in pivot style family and the workbook's own pivot table styles). Left out on purpose: EMF/WMF pictures (a vector interpreter with fonts, transforms and object tables is out of proportion for a placeholder that is already reported), pivot-area formats that pick items through `references` (they need the pivot cache and the table's layout to map items to cells), and secondary axes on scatter/bubble charts
   - Milestone 7 ✓ (pivot-area formats that pick row or column items through `references`, mapped to cells with the table's item lists in compact, outline and tabular layouts; secondary axes on scatter and bubble charts; single-strip JPEG-in-TIFF pictures; trendline label number format and manual position, turned axis labels, per-point data labels and a manually sized legend; tiled and translucent picture fills, glow, soft edges and rotated groups; R1C1 `INDIRECT` with whole rows and columns). Decisions: EMF/WMF stay placeholders — of the 2569 workbooks found on the development machine only one holds EMF pictures (six 1.4 KB solid-fill bitmaps with no text, in a workbook of 13 that hold any picture), while real pasted EMFs (charts, diagrams) are full of text, font objects and EMF+ records, so a minimal interpreter would draw most of them wrongly and silently rather than as a reported placeholder; no function outside the supported set turned up in the 246 conditional-formatting sheets of those workbooks, so the function list was not widened; first-page and even-page header pictures are not told apart, because the VML ids Excel gives them could not be verified (no workbook with header pictures was available) — such a header uses the picture of its section's default variant

Verified: unit tests and a python-pptx deck (default style with a 2×2 merge, a cell fill, a bottom-anchored cell, a red run; first column, last row and column bands) compared with LibreOffice 25: fills, borders, merges and text positions match. Difference: the header row, first column and last row are bold here, as the style's `b="on"` asks and PowerPoint draws them; LibreOffice draws them regular. Rows grow to fit their cells' text (a merged cell grows its last row by what its rows lack) and the rows below move down; borders follow. Shapes with `spAutoFit` grow taller to fit their text, keeping their top, and never shrink (`SlideLayout.cs`, `FitText`; slides only, the XLSX showcase renders unchanged). Verified: unit tests and a python-pptx deck (three short `spAutoFit` text boxes anchored top, middle and bottom; a table with 0.4" rows and a long cell) compared with LibreOffice 25: the table rows grow the same way. Difference: LibreOffice keeps the saved frame of an `spAutoFit` box and lets the text overflow around its anchor until the box is edited; it is grown here, as the spec and PowerPoint size the shape to its text. Vertical text (`bodyPr vert`, and `tcPr vert` in table cells; read by the shared DrawingML reader, so XLSX shapes get it too) is laid out across the height of the text area and turned about its center: `vert` runs down, `vert270` up, and the anchor follows the turned text (top-anchored `vert` text sits at the right). Stacked vertical text (`eaVert`, `mongolianVert`, `wordArtVert`, `wordArtVertRtl`) is drawn horizontally with a note. Vertical text does not grow `spAutoFit` shapes or table rows. Verified: unit tests and a python-pptx deck (`vert`, `vert270`, middle-anchored `vert`, `eaVert` boxes; a table with `vert` and `vert270` cells) compared with LibreOffice 25: the boxes match; the XLSX showcase is unchanged. Differences: LibreOffice puts top-anchored `vert` text in a table cell at the cell's left, where its own text boxes put it at the right as here, and it draws `eaVert` Latin text like `vert`. Spacing was checked on a python-pptx deck (two bullet levels, 12 pt before with 1.5 lines, an exact 40 pt pitch with 18 pt after) against LibreOffice 25: bullets, margins and line positions match, with lines drifting up to about 2 % higher over a full body, likely because LibreOffice's proportional spacing counts the font's line gap. Charts (`c:chart` in a graphic frame) go through the chart reader shared with XLSX (`src/Shared/DrawingMl/DmlCharts.cs`, with number formats in `src/Shared`), from the chart part's cached values; the embedded workbook is not opened, so a chart without caches draws empty. Its scheme colors follow the slide's color map, and a chart area without its own fill and outline is transparent and unframed, as PowerPoint and LibreOffice draw it (XLSX keeps Excel's white area with a gray outline). Verified: a unit test and a python-pptx deck (clustered column with a legend, pie with percent labels, line with markers) compared with LibreOffice 25: bars, slices, lines, categories and legends match. Presentation charts differ from XLSX ones in three defaults, given by the reader's `IChartData` (`TextColor`, `PresentationTitle`) so XLSX output is unchanged: text without a color of its own takes the theme's text color through the slide's color map (`tx1`) rather than Excel's dark gray; data labels inside bars and slices keep that color rather than one picked for contrast; and a title without its own size is 1.2 times the chart's text size and bold, as PowerPoint and LibreOffice draw it (Excel keeps 14 pt). The chart's text size is the chart space's `txPr` size, 10 pt without one; python-pptx writes 18 pt, which LibreOffice uses too. Verified: a unit test and the same deck compared with LibreOffice 25: title, text color and pie labels now match; the XLSX showcase is unchanged. A short chart gets fewer value-axis intervals (`IChartData.FitAxisToHeight`, presentations only; plot height taken as 75 % of the frame, 55 % with a title, about 2.2 lines of text per interval), so tick labels no longer overlap; LibreOffice drops most labels on short axes instead, and the fractions are estimates, not compared with PowerPoint. Markers of line, scatter and radar series are drawn 5 points across (the ISO 29500 default of `c:marker/c:size`, 2-72) in both XLSX and PPTX, and an explicit `c:size` wins in both. `c:marker/c:symbol` picks the shape: circle, square, diamond, triangle and dot are filled, plus, x and star are stroked 1.5 points wide in the series color, dash is a short filled bar, and `none` draws no marker; a marker without `c:marker/c:spPr` styling sits on a white halo 1.4 points wider, and a legend entry that shows a marker uses the same shape and colors. `c:marker/c:spPr` styles the marker: `a:solidFill` (scheme colors through the color map, tint/shade, `alpha`) or `a:noFill` fills it, and `a:ln` (color, `w`, `a:noFill`) outlines it, 0.75 points wide when no width is given; the fill is drawn first, then the outline, and a styled marker has no halo. A marker whose `spPr` states neither fill nor outline color is unstyled; an unstated fill is the series color and an unstated outline is none, so `a:noFill` alone draws nothing. Plus, x and star have no interior and are stroked with the outline's color and width, else the fill's color, else the series color; `a:ln` with `a:noFill` hides them. A marker with `a:noFill` and an outline is hollow, and one with no fill and no outline is not drawn. A data point's own marker (`c:dPt/c:marker`, matched by `c:idx` to the position in the series' values, null values counted; an out-of-range or missing `c:idx` is ignored) overrides the series' marker per aspect: a point's `c:symbol`, `c:size`, fill and outline are used when it states them and otherwise come from the series, so a point that gives only a fill keeps the series outline, `symbol="none"` hides that point's marker, and a point with a visible symbol on a series with none draws just that marker; the legend uses the series' marker only. A `c:dPt` with `c:spPr` but no `c:marker` does not recolor line segments. `auto`, an absent `c:symbol` and `picture` (no image support here) are drawn as circles: ISO 29500 only says the application selects an automatic symbol and defines no rotation of shapes, so none is invented and automatic output keeps circles; an unknown value reads as automatic. How PowerPoint sizes a marker that has no `c:size`, and the sizes of the dash and dot shapes, are estimates, and the explicit shapes are not compared with Excel or PowerPoint. Verified: unit tests and a throwaway deck (one series per symbol) rendered to PDF and viewed as PNG. SmartArt (`PptxContext.ReadDiagram`) is drawn from the drawing PowerPoint saves with each diagram (`dsp:drawing`, found through the data part's `dsp:dataModelExt relId`), read as a group filling the graphic frame through the same shape reader, with pictures resolved against the drawing part; a shape whose text box (`dsp:txXfrm`) differs from its frame is drawn as the shape and an unfilled text box over it. The diagram's data, layout and style parts are not evaluated, so a diagram saved without a drawing (by some older or third-party writers) is skipped with a warning. Verified: unit tests and a deck with a hand-made three-step process diagram (rounded rectangles with inset text boxes and arrows, theme fill and white `fontRef` text) compared with LibreOffice 25, which also draws the saved drawing: shapes, fills and text match. Speaker notes are out of scope for PDF. Embedded and linked objects (OLE) are drawn from the preview picture saved with them, as LibreOffice does; the object itself is not opened; previews saved as EMF/WMF (PowerPoint's usual icon format) are drawn through the metafile player (see Pictures). Not done: ink drawings and objects without a preview picture (each warns once); PNG output (not offered: the converter writes PDF only). DrawingML `tint` and `shade` (shared with XLSX shapes and charts) are applied in linear RGB, as LibreOffice's oox import does, so a 75 % tint of black is #898989
